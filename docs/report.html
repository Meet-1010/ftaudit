Free-threading audit · CPython 3.14.4t

What the GIL Was Hiding

PEP 779 made free-threaded Python officially supported in 3.14. I built a toolkit to find the thread-safety bugs that the GIL had been papering over, pointed it at 79 installed packages, and found five — including a hard interpreter crash that has been fixed on main for six days and never backported to a supported release.

Scope 79 packages · 4,726 files Host macOS 15 · arm64 · 10 cores Date 2026-08-25
The method

Same interpreter. Same wheels. One variable.

A free-threaded build can put the GIL back with PYTHON_GIL=1. That turns “this is a free-threading bug” from an assertion into a controlled A/B — the same binary, the same installed packages, the same script, with the lock as the only difference. Every claim below is stated that way.

The instrument

ftaudit

Existing tooling runs a project’s existing tests in parallel. The official free-threading guide is explicit about the gap: it “cannot discover issues from multithreaded use of data structures defined by your library.” Tests exercise one object each; the races live in the shared module-level state no test contends on. Three passes, zero dependencies.

ftaudit scan

Fourteen lock-aware AST rules. Walks only function bodies — module-level mutation runs once under the import lock and is not a race. Tracks lock depth, recognises correct double-checked locking, treats setdefault as atomic.

ftaudit gilcheck

Imports every dependency in a fresh subprocess and samples sys._is_gil_enabled() before and after. Catches the extension that silently switches the GIL back on for the whole process.

ftaudit stress

Barrier-released workers that assert an invariant, so “no exception” is never mistaken for “no bug”. Escalates thread count, then re-runs the whole campaign under PYTHON_GIL=1.

$ ftaudit stress findings/reproducers/pyyaml_add_constructor.py --trials 20

  GIL disabled    20/20 failed (100%)

  => reproduces only with the GIL disabled: a free-threading-specific defect.

Keeping the false-positive rate honest

Two threads iterating one generator segfault the interpreter

The documented behaviour is ValueError: generator already executing. Instead the process dies with SIGSEGV, SIGBUS, or Fatal Python error: _TAIL_CALL_CACHE — no Python-level exception, so it is uncatchable. The fix series for gh-120321 landed on main and closed on 2026-08-19; every PR is labelled 3.15 only. Objects/genobject.c on main has 38 FT_ATOMIC_* frame-state guards. The 3.14 and 3.13 branches have zero.

Undeclared extensions switch the GIL back on for everyone

An extension that never sets Py_mod_gil = Py_MOD_GIL_NOT_USED makes CPython re-enable the GIL process-wide at import. All three ship cp314t wheels, install cleanly, and look supported. The cost is paid transitively: import bs4 re-enables the GIL, because BeautifulSoup imports lxml — neither contains a line of at-fault code.

Concurrent registration silently loses constructors and resolvers

Every registry uses the same copy-on-first-write idiom: test cls.__dict__, copy the inherited dict, store. Two threads both find it absent, both copy the parent dict, and the second assignment discards the first thread’s. That registration is gone with no error — the tag simply fails to resolve later, far from the cause. Six methods across constructor.py, representer.py and resolver.py.

The log handler gets installed twice

_log() has two check-then-act races stacked — _logger is None and _has_level_handler() — plus a publication bug: it assigns _logger before configuring the level and handler, so another thread can pick up a half-built logger. Result: every werkzeug log line printed once per extra handler.

where() orphans its resource context managers

Concurrent callers all pass the is None test; each enters its own context manager and registers its own atexit hook, but only the last _CACERT_CTX survives. Under zipimport, as_file extracts a temp file — so an orphan is a file nobody cleans up, and the duplicate hooks can delete a path another thread still holds.

the whole reproducer
def gen():
    while True:
        yield 1

g = gen()
barrier = threading.Barrier(2)

def worker():
    barrier.wait()
    for _ in range(3000):
        try:
            next(g)
        except ValueError:
            pass          # the documented, correct outcome
Honest limits

What this does not show

  • One platform. Everything was reproduced on macOS 15 / arm64 only. These are data races; timing elsewhere will differ. The 3.13.13t two-thread cell (2/20) shows how sensitive that is even on one machine.
  • Narrow triggers on two findings. PyYAML and Werkzeug need registration or first-log to happen concurrently, which many programs never do. Real correctness bugs, limited blast radius — the write-ups say so.
  • certifi is not free-threading-specific. It reproduces with the GIL on too (1/200 vs 200/200). It should be filed as a general thread-safety bug, not a regression.
  • “Re-enables the GIL” is a packaging fact, not an accusation. Those extensions may well be thread-safe and merely undeclared. Only an audit settles it, which is why the ask is a tracking issue rather than a drive-by PR adding the flag.
  • No issues have been filed. The reports, reproducers and patches are written and verified; submitting them upstream is a decision for a human, not the tool.
